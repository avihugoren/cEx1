Where NVLink code runs

NVLink code runs in four places, and none of them touches the data

Software sets the links up and watches them. Once a link runs, every flit moves through pure hardware. The code lives on the host CPU, in GSP firmware, in the MINION controller of each link block, and in the NVSwitch.

Based on NVIDIA’s open-source GPU kernel driver · Hopper-era names

GPU architecture

Start outside in: control on top, compute in the middle, memory and links at the bottom

Control

Gets work in

PCIe brings commands from the host. The front end reads them. Copy engines move big blocks of data.

Compute · GPC → SM

Does the math

8 GPCs × 18 SMs on the full die. H100 SXM5 enables 132 of them.

Crossbar · L2

Joins compute to memory

Every SM reaches every L2 slice through the crossbar. All memory traffic, local or remote, passes the L2.

HSHUB · IOCTRL

The NVLink exit

HSHUB sends L2 traffic to the right link. Each IOCTRL block holds the link layers and a MINION.

GSP

The firmware brain

A RISC-V core that runs GSP-RM, the part of the driver that moved onto the GPU.

Memory controllers

Talk to HBM

Five HBM3 stacks on H100 SXM5: 80 GB at 3.35 TB/s.

Data path

A remote load crosses six hardware blocks and runs no code

Bring-up

At boot, the four code owners hand the link from one to the next

Remember

Four things to keep in your head

  1. The GPU has three bands: control on top (PCIe, front end, GSP), compute in the middle (GPCs, SMs, L2), memory and links at the bottom (HBM controllers, HSHUB, IOCTRL).
  2. NVLink data never runs through code. TL, DL and PHY are hardware.
  3. NVLink code runs in four places: the host driver, GSP-RM, the MINION in each link block, and the NVSwitch firmware.
  4. Firmware configures the links at bring-up and reacts to errors afterwards. That is where you will spend your time.
